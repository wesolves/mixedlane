Flowboard is where this team plans and tracks work (Flowboard MCP server: `flowboard`).

- **When you make a plan or receive requirements** (a feature, a bug list, a spec, "build X"), record the work in Flowboard with the `create_plan` tool: epic (the outcome) → milestone (if the project uses them) → user story (user value; acceptance criteria as a `- [ ]` checklist) → task (a concrete implementation step) → subtask. Use only the item types the project enables, `search_items` first and reuse what exists. Follow your Flowboard planning mode (see `whoami`): AUTO → create right away and tell the user the keys; PROPOSE → show the preview and create only after the user approves.
- **While you work**: `start_work` before you start an item; put its key in branch names, commit messages and PR titles (e.g. `APP-0012-add-login`) so GitHub links them; `add_comment` for decisions and blockers; `complete_work` with stage `review` when your part is done (`done` if there is nothing to review).
- **Specs and designs** longer than a few paragraphs go to Flowboard docs (`create_page`) and mention the item keys so they link both ways.
- If the repository has a `.flowboard.json`, use its `project`. If not and you need one, use the `flowboard-init` skill to link the repo to a project. For a brand-new initiative with no fitting project, create one with `create_project`; if that's not allowed, tell the user the exact setting named in the error.
